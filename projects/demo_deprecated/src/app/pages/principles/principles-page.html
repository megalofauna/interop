Interop is built on the premise that the web platform already implements most of what a component library wants to ship. These are the principles that follow from it.

"Platform-native" means a component's behavior derives from the browser. If a behavior can be so derived, it should be.

The web platform already implements most of what a component library wants to ship. Dialogs, popovers, disclosure, focus management, form semantics, and the accessibility tree are all browser features. Interop reaches for those first and adds coordination, tokens, and ergonomics on top, with the semantics left intact.

A popover trigger sets popovertarget and the browser does the rest. No JavaScript sits in the click path.

In the rare cases where the platform is lacking, Interop patches it.

The Accessible Rich Internet Applications standard (ARIA) supplies attributes for roles, states, and relationships that the HTML vocabulary cannot express on its own. It is an enormously useful addition to the web platform.

It is also the last thing a developer should reach for. The W3C's own guidance leads with it: no ARIA is better than bad ARIA.

Every role you write is a promise about behavior that you now own. role="tree" commits you to roving focus, typeahead, arrow-key expansion and collapse, and a selection model. Write the role, inherit the contract.

Chances are the platform has you covered.

In design, constraints aren't what's left over once the good ideas have been had. They're what makes the good ideas findable at all. Fourteen lines is not what the sonnet has to put up with. It's what the sonnet is.

Accessibility is a constraint of that kind. It applies early, and to the API rather than the output. It rules things out, which is the point. A design only some people can use never becomes a component.

Choosing a tier

Interop eschews extraneous wrappers. When semantics count, which is nearly always, components attach to standard HTML elements through attribute selectors.

The element you write is the element that ships.

Those accustomed to libraries built from custom elements may find this odd, or even off-putting. Does Interop expect me to ship a bare, unwrapped <label> as a componentized radio control?

Yes. Here's why.

There is no generated wrapper and no shadow root, so the semantics come standard. <fieldset> groups. <label> associates. <progress> announces. <button> handles keyboard activation and form participation. None of it is restated in ARIA, because none of it needs to be.

Restyling a component library should not feel like a fight. Interop ships every rule inside the interop cascade layer, with every selector wrapped in :where().

Two mechanisms doing two jobs. :where() holds every library rule at zero specificity, so ordering inside the library never depends on selector weight. The layer settles ordering against you: unlayered CSS beats layered CSS regardless of specificity, so anything you write outside a layer wins on contact.

Zero specificity on its own would not have been enough. A library that ships unlayered rules at (0,0,0) still beats a Tailwind utility at (0,1,0), because the utility is layered and the library is not. The layer is what makes the promise true.

Override once. Override again a layer down. Override a single instance inline. No !important, and no ::ng-deep.

A component should cost what you actually use. Interop splits its surface into tiers you import separately, and the bare attribute needs no import at all.

Three tiers, three separate decisions. A button that only needs to look right carries none of the code that makes one behave.

Where the platform is close but not yet everywhere, Interop ships the supporting code and the native attributes side by side, so adoption becomes a deletion rather than a rewrite.

Popover placement is the working example. InteropPopover delegates to a position strategy that defaults to Floating UI, while the directive already writes anchor-name and position-anchor on the elements. When CSS anchor positioning reaches baseline, the provider swaps and the JavaScript strategy becomes a no-op. interop-indicator already ships both paths behind @supports, and the fallback removes itself wherever support exists.

A good Interop release removes more code than it adds.

Docs are written alongside the component rather than after it. This site is built from the library it documents. The API tables are interop-table, the code samples are the code-block composite, the section nav derives its links from the sections themselves, and on a narrow viewport the nav drawer is a native popover toggled by an invoker command.
