Drag-to-resize wrapper with two performance tiers. Pure-CSS resize by default (zero JS in the resize loop); enhancement features — keyboard, snap-to-breakpoints, dimension readout, aspect lock — activate implicitly when their inputs are set.

The directive picks one of two tiers by the inputs you set. With no enhancement input it stays on Tier 0 — browser-native resize, nothing in the resize loop. Any of breakpoints, showDimensions, keyboard, aspectLocked, or liveResize upgrades it to Tier 1, a custom handle the directive drives itself.

Browser-native resize: both — no pointer listeners and no Angular change detection during the drag. Drag the bottom-right corner. The host is also a container-query container, so content inside can respond to its width. [min] / [max] feed the CSS bounds and [initialSize] seeds the starting size.

Each size bound is one CSS custom property:

  • --itx-resizable-min-width / --itx-resizable-min-height
  • --itx-resizable-max-width / --itx-resizable-max-height

The Protocol theme sets a default for each. Override it in one of two places.

CSS — a scoped default. Declare the property on an ancestor to set every resizable in that scope, or on the host for one: 

[interop-root] { --itx-resizable-min-width: 12rem; }

[min] / [max] inputs — one instance. The directive writes the same custom property inline on the host, so the input overrides an ancestor default through the normal cascade: 

<div interop-resizable [min]="{ width: 200 }" [max]="{ width: 720 }">…</div>

Both paths resolve to the same property, so both tiers enforce the bound identically. In Tier 0, native CSS resize reads the min/max-inline-size the token feeds — no script runs during the drag. In Tier 1, the drag loop reads the inputs when it clamps.

Choose by scope:

  • CSS token — a default across many instances, or when you already configure in CSS.
  • [min] / [max] inputs — one instance, or a value that changes at runtime.

The input is a per-instance override of the same token. Nothing else differs.
