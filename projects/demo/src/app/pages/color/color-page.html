Two axes, and nothing in between. A component declares that it is a layer — never which grey it is — and its surface, borders and text all follow from the depth it happens to sit at.

Elevation is the substrate you stand on. Contrast is everything drawn on top of it. They are different kinds of thing, so they are written differently: elevation is always a spatial word, contrast is always a bare scalar. You cannot spell one in the other's notation.

Moves toward light in both schemes. The light page is a mid-grey climbing to white; the dark page is near-black climbing to charcoal. Backgrounds only.

Contrast

--itx-contrast-1 … --itx-contrast-6 --itx-contrast-<family>-N

Moves away from the current surface, so its direction flips per scheme — darker in light, lighter in dark. A rank is a contrast target against whatever it sits on, not a fixed grey, which is why it stays correct at every depth and survives a hue change.

The label on each fill is derived, not chosen, and the ratio under each one is measured — read off the rendered swatch in the browser, not copied from the generator. Cream Can comes out with dark text because white on it measures about 1.7:1, a correction that used to live in a comment and had to be remembered by whoever added the next hue.

A seed's chroma is an intent, not a promise. Every hue has its own ceiling in sRGB, and the arc below the line is where a default-strength seed gets clamped — which is why a lightness-indexed slot ramp could not survive a hue change, and a contrast target can.

A state is not a lighter or a darker version of the fill — it is a step away from the label, so a state can only ever improve the contrast the solver proved for the rest state. Which means the direction is not a constant. Jelly Bean carries a light label and darkens; Cream Can carries a dark label and lightens. Same rule, opposite result.

The rules precede the componentry, so components cohere without agreeing on anything. That must never make overriding harder — every library selector is zero-specificity and sits inside the interop cascade layer, so any rule you write wins on contact.

Override through a component's own namespace (--itx-dialog-background), which no layer block ever touches. The generic --itx-surface and --itx-contrast-* are written by the engine at every boundary, so setting those on an ancestor is overwritten one layer down — by design, and asserted in the spec so the reason stays visible.

To move the whole palette instead, set --itx-tint-light / --itx-tint-dark (chroma and hue) or any --itx-ramp-*-light / -dark lightness number on any ancestor. Those stay unresolved until each layer composes them, so an override reaches every layer below it.
